<objective>
## Phase Goal

**As a** SillyTavern user, **I want** editing, deleting, or sending a message to clear my queued swipes with a clear explanation, while Continue and manual swipes leave them alone, **so that** queued swipes never get attached to a message that is no longer what I queued them for.

Purpose: GUARD-02 policy (D-04, D-05, D-06). Introduces `src/lifecycle.js` (pure policy, injected bridge/store/runner/toast) which later plans extend with chat-switch, popups, ownership.
Output: lifecycle module, store `clear`/`refingerprintAll`/`onReset`, accumulator reset, wiring in index.js, unit tests.

Researcher open question A6 resolved: the extra MESSAGE_RECEIVED trigger is INCLUDED (id greater than target, type not 'swipe'/'continue'), because an empty-textarea send appends an AI message with no MESSAGE_SENT and would otherwise leave items silently dropped as stale with no explanation.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ST/extension events to lifecycle | Any extension may emit MESSAGE_* with arbitrary args |
| Toast text | Interpolated count only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Tampering | queued result attached to an edited/deleted message | mitigate | Clear + invalidate + abort discard on edit/delete/sent; epoch discard in runner (plan 01); fingerprint recheck remains |
| T-04-07 | Tampering | Continue mis-detected, re-fingerprinting a really edited message | mitigate | Only re-fingerprint when generation type was 'continue' AND chatId/integrity/length unchanged AND mesId is last |
| T-04-08 | Denial of service | spoofed MESSAGE_EDITED clears the queue | accept | Self-inflicted by installed extensions; no spend impact |
| T-04-09 | Tampering (XSS) | toast text | mitigate | Only static literals plus an integer; toastr message string, no HTML from data |
</threat_model>
