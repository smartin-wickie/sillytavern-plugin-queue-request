# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by bm-ui-researcher, verified by bm-ui-checker.

**Context note:** This is a vanilla jQuery/ES-module SillyTavern (ST) UI extension, not a React/Next/Vite app. The `shadcn` gate (`<shadcn_gate>`) does not apply — there is no `components.json`, no npm build step, and CLAUDE.md locks this project to ST's existing jQuery + template-HTML conventions. This contract therefore specifies **how to extend ST's existing look**, not a new design system. Where the generic UI-SPEC template assumes a token-based design system (hex colors, independent spacing/type scale, component registry), this document adapts those sections to "inherit from ST, do not override" rules and says so explicitly rather than inventing values ST doesn't have.

Phase 2 introduces exactly three new visible surfaces: (1) a queue-swipe control icon next to the swipe arrows, (2) a count/running badge attached to that control, (3) a non-modal failure toast. Cancel UI, per-item list, progress bar, and settings panel are Phase 3 — out of scope here.

## Spacing Scale

Declared values (must be multiples of 4), for reference only — **the binding rule for this phase is pixel-parity with the existing sibling controls**, not an independently chosen scale:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between the new queue-control icon and the existing `.swipes-counter`/`.swipe_right` it sits after (D-02) |
| sm | 8px | Badge inset/padding if the badge needs its own box (keep minimal — prefer a borderless number+icon over a padded pill) |
| md | 16px | Not used this phase (no new section-level layout introduced) |
| lg–3xl | 24/32/48/64px | Not used this phase |

Exceptions:
- **Icon touch target**: match the existing `.swipe_right`/`.swipe_left`/`mes_button` icon size and click-target exactly (do not invent a 44px touch target in isolation — a new control sized differently from its row siblings reads as broken, not accessible). Confirm the live computed size via the claude-in-chrome smoke test (D-11) before finalizing `style.css`; do not hardcode a size guessed from memory.
- Badge, if it needs an offset to sit as a corner-notification on the control icon, use `-4px`/`-4px` top/right offset (xs token, negative) — standard notification-badge overlap, not a new scale value.

## Typography

No new type scale is introduced. All new text in this phase inherits its computed font (family, size, weight, line-height) from its DOM context — this is itself the contract, and it is binding:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | inherit from `.last_mes` | inherit | inherit |
| Label (badge number, tooltip text) | inherit from `.swipes-counter` sibling (ST's existing swipe pager uses a small compact size for its `{n}/{total}` text — match that, do not pick an independent px value) | inherit | inherit |
| Heading | not applicable — this phase introduces no heading-level text | — | — |
| Display | not applicable — this phase introduces no display-level text | — | — |

Tooltip text ("Queue a swipe" / "Queue full (5/5)") renders via the native HTML `title` attribute (ST's own message buttons use `title`, not a custom tooltip library) — no font override is possible or wanted there; it uses the browser's native tooltip rendering.

Toast text uses toastr's own default styling (ST global `toastr`) — do not override toastr's CSS.

## Color

No hex values are declared. ST ships a user-switchable theme system; a hardcoded hex would break for any theme other than the one it was eyeballed against. The binding rule:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `inherit` / no override | Control icon and badge render in the page's inherited text color (`currentColor`), exactly like sibling `.swipe_right`/`.swipe_left` icons |
| Secondary (30%) | `inherit` / no override | No new surface/background is introduced — the control sits inline in the existing message-button row, no new background color |
| Accent (10%) | Font Awesome icon swap, not a color | This phase has no accent color budget. The one state that needs to stand out — "an item is actively running" — is conveyed by swapping in a `fa-spinner fa-spin` icon next to the badge count, not by introducing a new color |
| Destructive | toastr's built-in `warning` style (default ST toastr colors) | Reserved for exactly one use this phase: the per-item failure toast (GUARD-05/D-09). No other destructive actions exist in Phase 2 (cancel UI is Phase 3) |

Accent reserved for: nothing new this phase — explicitly no accent color is introduced. (If a future phase needs a "queue full" visual warning beyond opacity, that is Phase 3's SET-01/UI-02 territory, not this phase's.)

Before writing `style.css`, verify the live computed color/opacity of a disabled `.mes_button`-style icon in ST 1.19.0 via the D-11 smoke test rather than guessing a CSS variable name from memory — this repo has no checked-out ST source or existing `style.css` to confirm variable names against.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (control tooltip, idle/available) | `Queue a swipe` (locked, D-03) |
| Primary CTA (control tooltip, at max) | `Queue full (5/5)` (locked, D-06) — the two numbers are live (`pending+running` / `maxQueueSize`), not literal "5/5" text |
| Badge content (queue non-empty) | Plain integer = pending count including the one currently running, e.g. `3`. When an item is actively running, prepend a `fa-spinner fa-spin` icon: `⟳ 3`. Badge is hidden entirely (not shown as `0`) when the queue is empty and nothing is running (UI-01) |
| Empty state | Not applicable — per QUEUE-08 / Roadmap Phase 2 SC1, the control is absent entirely in group chats and chats with no AI message to swipe. There is no "queue is empty, click to add" empty-state copy to write; the control's normal idle tooltip (`Queue a swipe`) already communicates the affordance when it is visible |
| Error state (GUARD-05 toast) | Exactly three locked variants, no raw backend text or stack traces ever surfaced (D-08): `Queued swipe failed: API error` / `Queued swipe failed: empty reply` / `Queued swipe failed: cancelled`. Rendered via `toastr.warning(msg, undefined, { preventDuplicates: true })` (D-09), default timeout |
| Destructive confirmation | Not applicable this phase — no cancel/delete action exists yet (QUEUE-06/07 cancel UI is Phase 3). Nothing to confirm |

## Interaction Contract (phase-specific, not in the generic template)

These are load-bearing for the executor and checker and are called out separately because the generic template has no section for them:

| Control | Idle (queue has room) | At max (queue == maxQueueSize, default 5) |
|---------|------------------------|---------------------------------------------|
| Queue-swipe icon (`fa-clock`, D-01 primary choice; `fa-layer-group` is the locked fallback icon if `fa-clock` collides visually with another button in the row) | Clickable, default icon opacity/color (inherits from sibling `.swipe_right`), `title="Queue a swipe"` | Disabled: `opacity: 0.5`, `cursor: not-allowed`, `title="Queue full (5/5)"` with live numbers — no color change, no new token |
| Click behavior | Enqueues one item; queue continues running/starts running; control stays interactive (can click again immediately, repeatably, up to max per D-05/QUEUE-02) | No-op (disabled) |
| Running indicator | **Never on the control icon itself** — no spin/pulse/badge-dot on the icon (D-07, explicit) | same |
| Badge | Visible whenever pending+running > 0; shows count; shows `fa-spinner fa-spin` + count while an item is actively generating | same rule; count simply reads `5` |

Placement (D-02, locked): the control sits to the right of the right swipe arrow, **after** the existing `.swipes-counter` element, inside the `.last_mes` message's button row. The badge anchors to the queue-swipe icon (top-right corner overlap, standard notification-badge pattern), not to the swipe counter.

Visibility gate (QUEUE-08): the entire control+badge cluster is not rendered (not merely disabled) in group chats and in chats where the latest message has no AI reply to swipe. Verify the exact DOM condition ST uses for "is this message swipeable" during implementation — not independently re-derived here, since `isSwipingAllowed()`/`swipe.isAllowed()` already exists on the bridge per `ARCHITECTURE.md` §1.8 and should be reused, not reimplemented.
