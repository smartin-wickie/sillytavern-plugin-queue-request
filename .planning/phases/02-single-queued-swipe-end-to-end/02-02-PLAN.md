    - `runner.wake()` does nothing (no generate() call) while `bridge.isGenerating()` is `true` or `bridge.swipeState() !== 'none'`
    - The runner never has two `generate()` calls in flight at once — a second `wake()` fired while one item is already running is a no-op until the first completes
    - On `fingerprintMatches` returning `false` for the next queued item, the runner calls `store.drop(item.id, 'stale')` and does NOT call `generate()` for that item, then immediately tries the following item
    - On `generate()` resolving with `{ text, meta }`, the runner calls `append(mesId, text, meta)`; if `append` returns `'ok'`, the runner calls `store.markDone(item.id)` and immediately attempts the next item
    - If `append` returns `'defer'` (ST became busy between generate() finishing and the append attempt), the runner retries the append on a short poll (every ~250ms) rather than dropping the item — this is the park-then-flush behavior (SWIPE-04)
    - If `append` returns `'stale'` after a successful `generate()`, the runner calls `store.drop(item.id, 'stale')` (the target changed while this item was generating) and discards the generated text — it is never retried or appended elsewhere
    - On `generate()` rejecting or resolving with a typed error object (e.g. `{ error: 'empty' }`), the runner calls `store.drop(item.id, reason)` and continues with the next item without throwing out of `wake()`
  </behavior>
