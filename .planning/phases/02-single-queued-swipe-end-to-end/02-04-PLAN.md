    - `createGuard({ bridge, runner }).start()` subscribes to `GENERATION_STARTED`, `GENERATION_ENDED`, `GENERATION_STOPPED`

    - When `GENERATION_STARTED` fires with `dryRun === true` (including the Runner's own capture, or any other extension's dry run, e.g. Prompt Inspector's `tryGenerate`), `runner.pause` is NOT called — only `dryRun === false` pauses

    - `runner.pause(reason)` sets an internal paused flag; while paused, `wake()` is a no-op (does not start a new item) even if items are pending; `resume()` clears the flag and calls `wake()` once
    - The Runner's existing fingerprint check (before `generate()`, from 02-02) is unchanged; a SECOND fingerprint check is added immediately before the `append()` call (after `generate()` resolves successfully), using a fresh `fingerprintMatches(bridge, item.fingerprint)` call — if it now fails, `store.drop(item.id, 'stale')` and the generated text is discarded without ever calling `append()`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| ST global event stream (`eventSource`) ↔ Guard | Any extension or ST core code can emit `GENERATION_STARTED`/`GENERATION_ENDED`/`GENERATION_STOPPED`; the Guard must not assume it is the only listener or the only emitter |
| Adapter error object ↔ UI toast text | The one place raw backend/network error detail could leak to the visible UI if not deliberately blocked |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-02-04-01 | Information Disclosure | `src/ui.js` (toast rendering) | mitigate | Exactly 3 static locked strings selected by reason-code lookup; never string-built from the underlying `Error`/response object; never `.html()` (Security Domain V5) |
| T-02-04-02 | Tampering | `src/runner.js` (second fingerprint check) | mitigate | GUARD-04's two-point re-validation closes the window between a successful generation and the append — an edit/delete/chat-switch landing in that window now reliably drops the item instead of writing to a stale target |
| T-02-04-03 | Denial of Service | `src/guard.js` (event handler re-entrancy) | mitigate | Handlers never `await` into `runner.wake()`'s generation path inline; scheduled via microtask/`setTimeout(0)`, so a slow handler cannot block `eventSource.emit`'s serial await chain for other listeners (Pitfall 6) |
| T-02-04-04 | Repudiation | `src/guard.js` (pause attribution) | accept | The Guard cannot distinguish *which* extension or user action triggered a non-dry `GENERATION_STARTED` — it pauses for any of them uniformly, which is the correct and safe default (GUARD-06's finer "native stop vs. queue cancel" distinction is explicitly Phase 4 scope) |

</threat_model>
