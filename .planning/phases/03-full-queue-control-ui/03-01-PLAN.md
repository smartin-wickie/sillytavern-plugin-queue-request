<objective>
Give the Runner the one genuinely new capability this phase needs — cancelling the item currently mid-generate() — and ship the first real control surface for it: a dropdown anchored to the existing queue badge where the user can cancel one pending item, the running item, or everything at once.

Today the per-item `AbortController` is created and discarded entirely inside `index.js`'s `generate()` closure; nothing outside that closure can reach it, so there is no way to implement "cancel running" (QUEUE-06) or the per-item cancel list (QUEUE-07). This plan moves that controller's ownership into `runner.js` (matching `ARCHITECTURE.md`'s original component table) and exposes `abortRunning()`, plus adds a success-side `onItemDone`/`offItemDone` pair that later plans in this phase (toast coalescing, progress bar) will also need. Everything else — per-item drop, cancel-all — reuses `store.drop()` with zero new store API, per `03-RESEARCH.md`'s Pattern 1/Pattern 2 and Assumptions Log A2.

Purpose: Unblock every cancel surface in this phase (dropdown, wand menu, slash commands, progress-bar stop all converge on `runner.abortRunning()` / the shared `cancelAll()` helper this plan creates) and ship the first of them end to end.
Output: `src/runner.js` (abortRunning/onItemDone/offItemDone), `src/queueActions.js` (new, `cancelAll`), `src/ui.js` (cancel dropdown), `style.css` (dropdown classes), `index.js` (generate() signature change), extended `test/runner.test.js`, new `test/queueActions.test.js`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| User click (DOM) ↔ dropdown cancel actions | Local, same-origin DOM events; no network/remote input involved |
| Extension's own AbortController ↔ ST's global generation state | `runner.js`'s `runningController` must never be confused with or substitute for ST's own `stopGeneration()`/global abort controller |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-03-01-01 | Tampering | `src/ui.js` dropdown per-item cancel | mitigate | Re-check `item.status === 'queued'` immediately before `store.drop()` to prevent a lost/misapplied cancel after the runner concurrently promotes the same item to `'running'` (RESEARCH.md Pitfall 1) |
| T-03-01-02 | Elevation of Privilege | `src/runner.js` `abortRunning()` | mitigate | `abortRunning()` only ever calls `adapter.js`'s `abortOwn(runningController)`; never calls ST's global `stopGeneration()` — the extension's cancel action stays scoped to its own in-flight request and never interrupts a user-initiated native generation |
| T-03-01-03 | Tampering | `src/ui.js` dropdown row rendering | mitigate | Dropdown rows are built from DOM nodes/`textContent` only (ordinal labels, no model/prompt text ever reaches this surface), never `.innerHTML` with dynamic data |
| T-03-01-04 | Denial of Service | `src/runner.js` `runningController` lifecycle | accept | A double "Cancel running" click is a no-op per `abortOwn`'s idempotent `ownController.abort()`/`signal.aborted` check — no crash risk, local-only, low-value target |

</threat_model>
