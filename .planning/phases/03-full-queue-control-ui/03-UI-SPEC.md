# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by bm-ui-researcher, verified by bm-ui-checker.

**Context note:** Same project as Phase 2 — a vanilla jQuery/ES-module SillyTavern (ST) UI extension, not a React/Next/Vite app. The `shadcn` gate does not apply: no `components.json`, no npm build step, CLAUDE.md locks this project to ST's existing jQuery + template-HTML conventions. This contract specifies **how to extend ST's existing look and the Phase 2 surfaces**, not a new design system.

Phase 3 extends the three Phase 2 surfaces (queue-swipe control icon, badge, failure toast) with five new ones: (1) a cancel dropdown anchored to the badge, (2) two wand-menu entries, (3) three slash commands (toast-only feedback, no chat-visible system messages per D-06/D-07), (4) a top-of-chat progress bar with a stop control, (5) a settings panel in the Extensions drawer. It also changes one piece of Phase 2 behavior: per-item failure toasts become coalesced (UI-03) — see Interaction Contract.

## Spacing Scale

Declared values (multiples of 4) for the genuinely new container surfaces this phase introduces (dropdown panel, progress bar, settings panel). Icon-level elements (per-item × button, wand entries, control icon) still follow Phase 2's binding rule: **pixel-parity with the existing sibling ST element they sit next to**, not an independently chosen scale.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between an icon and its label inside a dropdown row or settings field (e.g. `×` to item text, checkbox to its label) |
| sm | 8px | Vertical padding of one dropdown row; vertical gap between stacked settings fields within one group; progress-bar inner vertical padding |
| md | 16px | Dropdown panel's outer padding (top/bottom/left/right); horizontal padding of the progress-bar container; gap between dropdown header and its row list |
| lg | 24px | Vertical gap between distinct settings field *groups* (e.g. between the enable toggle and the numeric-input cluster) inside the settings drawer content |
| xl–3xl | 32/48/64px | Not used this phase — no page-level layout is introduced |

Exceptions:
- **Progress bar height**: 4px filled track (thin bar, matches the competitor precedent "top-of-chat progress bar" in FEATURES.md) inside an 8px-padded container — the 4px track itself is a declared exception to the "multiples of 4 for spacing" rule because it is a visual fill indicator, not a spacing gap.
- **Stop control / per-item cancel (×) touch target**: match the existing `.qs-queue-control` icon sizing from Phase 2's `style.css` (25px, pixel-matched to `.swipe_right`) — do not invent a different size for icons that sit in the same visual family.
- **Dropdown panel max width/height**: cap at a reasonable scrollable size (e.g. `max-height: 320px; overflow-y: auto;` is a sensible default) rather than letting a 20-item (hard max) pending list grow unbounded; exact value confirmed during implementation against the live ST layout, not guessed from memory.

## Typography

No new type scale is introduced. All new text inherits its computed font (family, size, weight, line-height) from its DOM context, exactly as Phase 2 established — this is binding:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | inherit from `#extensions_settings2` / `.last_mes` context, depending on surface | inherit (ST's default extension-settings body weight, normal/400) | inherit |
| Label (dropdown per-item text, settings field labels, slash-command toast body) | inherit from the nearest existing ST convention: dropdown rows inherit `.swipes-counter`'s compact size (same rule as Phase 2's badge); settings field labels inherit whatever size ST's own `inline-drawer-content` labels already use elsewhere in the Extensions drawer | inherit | inherit |
| Heading (dropdown header "Queued swipes", settings drawer header) | inherit from ST's own `.inline-drawer-toggle b` convention already used by every other extension's settings section header — do not pick an independent px value | inherit (ST's own drawer headers render bold via the `<b>` tag; this is inherited markup, not a new weight choice) | inherit |
| Display | not applicable — no display-level text in this phase | — | — |

Exactly 2 weights are in play, both inherited, never explicitly set: ST's default body weight (normal) for everything except the settings drawer header `<b>` (bold), which is ST's own existing markup convention, not something this phase introduces.

Toast text (slash-command feedback, coalesced completion/error summaries) uses toastr's own default styling — do not override toastr's CSS, same rule as Phase 2.

## Color

No hex values are declared — same binding rule as Phase 2: ST ships a user-switchable theme, a hardcoded hex breaks under any theme other than the one eyeballed against. New this phase: one accent reservation and one destructive reservation, both still expressed as "reuse ST's existing variable/class for this role," never a literal color.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `inherit` / no override | Dropdown panel text, settings field labels, progress-bar container background all render in inherited page colors — no new surface color is invented |
| Secondary (30%) | Reuse ST's existing popup/dropdown surface styling (the same background/border treatment ST's own context menus or the Extensions drawer content already use) | Cancel dropdown panel background + border; settings drawer content background (it already inherits this for free by living inside `#extensions_settings2`) |
| Accent (10%) | Reuse ST's existing accent CSS variable (commonly a variable in the `--SmartTheme*` family, e.g. the one ST's own progress/loading indicators already use) — **do not hardcode a hex**; confirm the exact variable name against the live ST install before finalizing `style.css`, per Phase 2's established "verify live, never guess from memory" rule | Reserved for exactly one element this phase: **the progress bar's fill** (UI-02). No other element gets this accent — not the dropdown, not the wand-menu entries, not settings fields |
| Destructive | Reuse ST's existing destructive/danger styling (the color ST's own delete/cancel-style buttons already use, e.g. a crimson/red variable) — again, verify the exact variable, do not hardcode | Reserved for exactly three elements: the per-item cancel (`×`) inside the dropdown, the "Cancel running" button, and the "Cancel all" button (D-01–D-04). The wand menu's "Cancel all queued" entry (D-05) also gets this treatment since it performs the same destructive action |

Accent reserved for: **the progress bar fill only** — explicitly not the control icon, not the badge, not any settings field (continuing Phase 2's "no accent color budget beyond one clearly-scoped use" discipline).

Destructive reserved for: **cancel actions only** (per-item ×, Cancel running, Cancel all, wand-menu Cancel all queued) — never used for the queue-swipe control itself, the progress bar, or any non-destructive settings field.

Before writing CSS for any new surface, verify the live computed color/variable names in ST 1.19.0 via a smoke test (same discipline as Phase 2's D-11) rather than guessing a `--SmartTheme*` variable name from memory — this repo has no checked-out ST source to confirm variable names against.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (wand menu, queue entry) | `Queue swipe` (D-05 — same verb as Phase 2's control tooltip "Queue a swipe", shortened to fit a menu-entry label convention) |
| Primary CTA (wand menu, cancel entry) | `Cancel all queued` (D-05, same action/scope as the badge dropdown's "Cancel all" per D-03) |
| Dropdown header | `Queued swipes` |
| Dropdown per-item row | Plain ordinal or short label per pending item, e.g. `Swipe request {n}` (no prompt text, no model name — items carry no distinguishing user-facing content pre-generation), each with a trailing `×` cancel icon (D-04) |
| Dropdown "cancel running" button | `Cancel running` |
| Dropdown "cancel all" button | `Cancel all` |
| Empty state (dropdown) | Not applicable as a persistent state — the dropdown can only be opened from the badge, and the badge is hidden whenever pending+running is 0 (Phase 2 UI-01 rule, unchanged). If the last item is cancelled/completes while the dropdown is already open, close the dropdown immediately rather than rendering an empty "nothing queued" panel — there is nothing left to anchor it to |
| Progress bar label | `{completed} / {completed + pending + running}` swipes — both numbers are live (grow if the user adds more mid-run, per the same "numbers are live, never a literal snapshot" rule as D-06/D-12), e.g. `2 / 5` |
| Progress bar stop control (tooltip) | `Stop queue` — performs the same action as "Cancel all" (D-03), not a separate semantic |
| Settings panel header | `Queued Swipes` (matches `display_name` in `manifest.json`) |
| Settings: enable toggle label | `Enable queued swipes` |
| Settings: max queue label | `Max queue size` (number input, 1–20, clamped client-side to `HARD_MAX_QUEUE` before saving, per D-11) |
| Settings: auto-jump label | `Jump to newest swipe on completion` |
| Settings: notification style label | `Notification style` with options `All` / `Errors only` / `Off` (D-09) |
| Settings: circuit-breaker label | `Pause after N consecutive failures` (number input, 1–10, default 3, per D-10 — stored only, no enforcement until Phase 4) |
| `/queueswipe [count]` feedback (clamped) | `toastr.info`: `Queued {added} swipe(s).` when count fits; `toastr.warning`: `Queue full — added {added} of {requested} requested.` when clamped (D-06). No chat-visible system message ever |
| `/queueswipe [count]` feedback (already full) | `toastr.warning`: `Queue is already full ({max} max).` |
| `/queuecancel` feedback | `toastr.info`: `Cancelled {n} queued swipe(s).` (D-07); if nothing was queued: `toastr.info`: `Queue is already empty.` |
| `/queuestatus` feedback | One-line summary, no per-item detail (D-08): `Queue: {running} running, {pending} pending ({max} max).` Empty case: `Queue: empty.` |
| Error state (per-item failure, Phase 2 taxonomy, now coalesced per UI-03) | Reuse the 3 locked reason strings from Phase 2 (`FAILURE_MESSAGES`: `api` / `empty` / `cancelled`), but roll up into one summary toast per drained run instead of one toast per item — see Interaction Contract below for the exact coalescing rule. Never raw backend error text |
| Completion summary (coalesced, UI-03) | `toastr.success`: `{n} queued swipe(s) completed.` when a run drains with zero failures; combined form when there are also failures: `toastr.warning`: `{completed} completed, {failed} failed ({reasons}).` where `{reasons}` is a short comma-joined list of the distinct failure categories seen (e.g. `API error, empty reply`), never a per-item breakdown |
| Destructive confirmation | **None, anywhere in this phase.** Per D-07's explicit "no confirmation popup" for `/queuecancel`, extended consistently to every other cancel surface (badge dropdown's per-item ×, Cancel running, Cancel all, the wand menu's Cancel all queued, and the progress bar's Stop control) — cancel is treated as low-stakes and instantly reversible by re-queueing, not a destructive-with-confirmation action anywhere in this extension |

## Interaction Contract (phase-specific, not in the generic template)

These are load-bearing for the executor and checker; the generic template has no section for them.

### Cancel dropdown (D-01–D-04)
| Trigger | Behavior |
|---------|----------|
| Click the badge (`.qs-queue-badge`) | Opens a dropdown anchored to the badge (not a modal). Lists each pending item (D-01) with a per-item `×`, plus `Cancel running` and `Cancel all` buttons in the same panel |
| Click a per-item `×` | Drops just that one pending item (D-04); does not touch the running item or other pending items; dropdown stays open, re-renders its row list live |
| Click `Cancel running` | Calls `adapter.js`'s `abortOwn(ownController)` (never ST's global `stopGeneration()`); drops the item with reason `'cancelled'` (reuses Phase 2's `FAILURE_MESSAGES.cancelled` taxonomy, now folded into the coalesced summary below, not a standalone toast); runner immediately advances to the next pending item (D-02) |
| Click `Cancel all` | Drops every pending item and aborts the running item via the same `abortOwn()` call (D-03); scope = pending + running |
| Pending+running count reaches 0 while dropdown is open | Dropdown closes immediately (its anchor, the badge, disappears per the unchanged Phase 2 UI-01 rule) |
| Click outside the dropdown | Closes it (standard dropdown dismissal, no confirmation needed since no destructive action requires one) |

### Wand menu (D-05)
| Entry | Behavior |
|-------|----------|
| `Queue swipe` | Identical action to clicking the Phase 2 control: `store.add()` + `runner.wake()`. Disabled/absent under the same QUEUE-08 gate as the control (group chats, no swipeable AI message) |
| `Cancel all queued` | Identical action to the dropdown's `Cancel all` (D-03) |

### Slash commands (D-06–D-08)
| Command | Behavior |
|---------|----------|
| `/queueswipe [count]` | `count` defaults to 1 when omitted. Clamps to remaining capacity (`maxQueueSize - (pending+running)`). Feedback is `toastr` only — never a chat-visible `/echo`-style system message |
| `/queuecancel` | No confirmation popup. Same pending+running scope as `Cancel all`. Reports cancelled count via toast and the command's string return value (scripting-friendly) |
| `/queuestatus` | One-line summary only, no per-item detail, via toast and/or command return value |

### Progress bar (UI-02, Claude's discretion per CONTEXT.md)
| State | Behavior |
|-------|----------|
| Pending+running > 0 | Progress bar renders at the top of the chat area, same show/hide rule as the badge (hidden entirely, not rendered empty, when the count is 0) |
| Each completion | Numerator (`completed`) increments by one; denominator recomputes live as `completed + pending + running` — grows if the user adds more via QUEUE-02 mid-run, matching the "numbers are always live" convention already used by D-06/D-12 |
| Click the stop control | Performs the exact same action as `Cancel all` (D-03) — not a separate cancellation code path |
| Pending+running reaches 0 | Progress bar hides; `completed` counter resets to 0 for the next run (a "run" is bounded by the queue going empty, not by a fixed batch size) |

### Toast coalescing (UI-03, Claude's discretion per CONTEXT.md — changes Phase 2 behavior)
**What changes from Phase 2:** Phase 2 fired one `toastr.warning` per failed item, immediately on failure. Phase 3 must coalesce: accumulate outcomes (success/failure + reason) for the duration of one "run" (from the queue leaving empty to it draining back to empty), and flush exactly one summary toast when the run drains, rather than one toast per item.
- If the run had zero failures: one `toastr.success` summary (`{n} queued swipe(s) completed.`), shown only when notification style is `All`.
- If the run had any failures: one `toastr.warning` summary combining completed count and a short, deduplicated list of failure reason categories (never a per-item breakdown, never raw error text) — shown when notification style is `All` or `Errors only`.
- Notification style `Off`: no completion/error toast at all; the badge and progress bar remain the sole feedback surfaces.
- This setting (D-09) controls toast verbosity only — it never affects the badge, progress bar, or dropdown, which always reflect live state regardless of notification style.

### Settings panel (SET-01, D-09–D-12)
| Rule | Detail |
|------|--------|
| Location | `inline-drawer` block appended to `#extensions_settings2`, loaded via `renderExtensionTemplateAsync` (per STACK.md convention) |
| Live-apply | Every field re-reads `extension_settings[MODULE_NAME]` at the point of use (mirrors `store.js`'s existing `getMaxQueueSize()` live-read pattern) — no reload or chat-switch required (D-12) |
| Max queue input | Plain number input 1–20, client-side clamped to `HARD_MAX_QUEUE` (20) before saving (D-11) — not a dropdown of presets |
| Circuit-breaker input | Plain number input 1–10, default 3 (D-10) — stored only this phase; Phase 4's GUARD-06 reads the same key, no enforcement wiring here |
| Notification style | Single setting controlling both failure and completion/coalesced toast verbosity (D-09) — not independent per-event-type toggles |
| Persistence | Saved via the existing SET-02 merge-by-key pattern into `extension_settings[MODULE_NAME]`, same object Phase 2 already established, not a new storage location |
